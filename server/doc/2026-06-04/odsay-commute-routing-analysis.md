# ODsay 통근 라우팅 분석 — 직선거리 게이트 문제 & 내부 지하철 라우터 (다음 세션 작업)

> 상태: **분석/설계 메모 (미구현)**. 다음 세션에서 진행 예정. 작성: 2026-06-04
> KI-24(재고 게이트)와는 별개 트랙 — 통근(commute) 축의 정확도 문제.

> **TL;DR** — ODsay 호출을 못 받으면 추천 랭킹이 **직선거리 기준**으로 매겨진다. 게이트 3중이
> 전부 직선거리라 "가깝지만 환승 많은 동네"(삼산동)는 과대평가되고, "멀지만 직통"인 동네는 후보에서
> 잘려 영영 안 보인다. ODsay 풀매트릭스 선캐싱은 무료쿼터로 **~3.6년**이라 런칭 경로가 아님.
> 해법 = **무료 내부 지하철 라우터를 1차 게이트로** + demand-driven ODsay 캐시를 정밀 마감에만 사용.

## 1. 발단 — 삼산동 케이스

- 삼산동은 부천에 직선거리로 거의 붙어있는데 실제 대중교통 **36분**(출근시간 8:56 실측). 기준선 30분 초과.
- 그런데 받아온 외부 순위는 삼산동을 3위에 올림 → **통근을 시간이 아니라 거리로 쟀다는 신호**.
- 의심: 우리 추천 알고리즘도 ODsay 응답을 못 받으면 거리기반 폴백을 타고, 그 값으로 랭킹이 매겨지는 것 아닌가?

## 2. 코드 확인 — 직선거리가 ODsay보다 먼저 3번 거른다

`server/src/services/repositories/recommendationRepository.ts`

| 게이트 | 위치 | 동작 |
| --- | --- | --- |
| ① 거친 사전필터 | `:937-944` | `maxKm = patience×1.2×0.5×1.3`. 직선거리 초과 동을 **universe에서 제외** (가격조차 안 봄) |
| ② 통근 게이트 | `:1008` | `commuteMinutes > patience×1.2 → continue`. 캐시 miss면 `estimateTransitMinutesByKm(직선거리)` 추정으로 컷 |
| ③ 정렬 | `pickTopRegions` (`scoring.ts:426`) | 살아남은 후보를 Haversine 통근점수로 줄세움 |

폴백 추정식 (`:43`):
```ts
function estimateTransitMinutesByKm(km: number): number {
  return Math.round(km / 0.42 + 5);  // 직선거리 ÷ 25km/h + 5분
}
```

핵심: **클라이언트 ODsay 실측(`commuteOverrides`)은 깔때기 출구의 top-8에만 돌고, 표시·지도색만
덮어쓴다. 랭킹/총점은 서버 직선거리값 그대로** (`MapPanel.tsx:97` 주석에 명시, 스토어
`setCommuteOverrides`는 재정렬 없음 `useRecommendationStore.ts:200`).

그리고 통근축은 안전·생활과 달리 `estimatedAxes` 제외 안전망도 없음 — 추정이어도 풀 가중치(35)로
총점 반영 (`scoring.ts:375`, `active: true`).

## 3. 두 종류의 오류 (둘 다 ODsay 보정이 못 잡음)

| 오류 | 정체 | 예시 (patience 30 → 직선 13km 컷) | ODsay 보정으로? |
| --- | --- | --- | --- |
| **거짓 음성** | 실제 빠른데 직선거리로 잘려나감 | 직선 14km인데 경인선 직통 28분인 곳 → 추정 38분 → 게이트 ② 탈락 | ❌ 후보에 없어 조회조차 안 됨. 영구 누락 |
| **거짓 양성** | 가깝지만 환승 많은데 상위로 샘 | 삼산동 직선 8km → 추정 24분 → 상위 랭크 → 클라 ODsay가 36분 밝혀도 이미 3위 고정 | ⚠️ 숫자만 보정, 순위 고정 |

→ **진짜 노선으로 골랐으면 top-8 구성이 통째로 달라질 수 있다.** 표시된 8곳은 "직선거리로 뽑힌 8곳에
ODsay 라벨만 나중에 붙인 것"이지 "ODsay로 뽑은 8곳"이 아님. **클라 재정렬만으론 거짓 양성만 부분 해결,
거짓 음성(서버에서 이미 사라진 후보)은 복구 불가.**

## 4. "ODsay 풀매트릭스 매일 선캐싱" 타당성

무료 쿼터(1,000건/일)로 수도권 전 행정동 매트릭스를 채우는 안 — **정확도 천장은 맞지만 런칭 경로가 아님.**

- 수도권 행정동 ≈ 서울 426 + 경기 ~560 + 인천 ~150 ≈ **1,150개**
- 디렉티드 풀매트릭스 = 1,150² ≈ **1,322,500쌍 ÷ 1,000/일 ≈ 3.6년** (대칭 가정 절반쳐도 ~1.8년)
- 그 사이 GTX·노선개편 한 번이면 초기 캐시 stale → **다 채우기 전에 앞부분이 썩음**
- **"격자 to 격자"는 불가능**: 현 캐시키는 3자리 격자 ≈ 111m (`odsay.ts:302`). 그 해상도면 origin/dest
  각 수십만 → 격자² = 10¹⁰+ . 행정동으로 내리면 계산은 되지만 centroid 오차(동 내 1~2km)로 "가장 정확"이 깨짐

별표: ODsay 자체도 시각표 기반 추정(실시간 혼잡 X), centroid 해상도, staleness.

**시간을 돈으로:** ODsay 유료(예 50,000/일) → ~27일. 주요 업무지구 200곳 × 1,150동 = 23만쌍만
선캐싱 → 무료로 ~8개월.

## 5. 권장 아키텍처 — 2단 (내부 라우터 = 1차, ODsay = 결승)

```
① 후보 universe → 거친 직선 사전필터 (넉넉하게)
② 내부 지하철 라우터 (쿼터 0)
   └ 환승인지 소요/환승수로 게이트②·정렬③ 교체  ← 거짓음성/양성 여기서 제거
   └ top ~20~30 으로 압축
③ ODsay 실측 (쿼터 ~20~30/조회)
   └ 살아남은 소수만 정밀화 → 최종 top-8 재정렬·표시
```

- 콜드패스(아무도 안 가본 직장): 내부 라우터가 즉시 커버, 쿼터 0
- 핫패스(강남·판교 등): 실사용 트래픽이 ODsay 캐시 자연 누적 → 점점 정밀화
- **이미 demand-driven 캐시가 있음** (`commuteRepository.ts` 9격자 KNN) = 정답의 절반. 풀 프리컴퓨트는
  오히려 런칭을 1.8~3.6년 후퇴시키는 것

## 6. 내부 라우터 설계 메모 (퇴근 후 작업용)

빠진 결정적 재료 = **지하철 노선 그래프**. 3재료 vs 현 자산:

| 재료 | 레포에 있나 | 실태 |
| --- | --- | --- |
| 정류장 배치 | △ 부분 | 서울 버스정류장 좌표 CSV(`seoulBusStopTransit.ts`) — 버스만, 밀도용 |
| 지하철 노선 | ❌ 없음 | `PoiSummary.subwayCount`는 역 **개수**뿐. 호선/역순서/환승역 정보 전무 |
| 배차시간 | △ 거의 없음 | `tagoClient`가 경기·인천 버스 배차만. 서울 `avgHeadwayMin: null`, 지하철 배차 0 |

→ **지하철 그래프 하나만 적재하면 쿼터 0 라우터 성립.** 수도권 역 ~750, 노선 ~23개 — 작고 정적이고
무료 (서울 열린데이터광장 / 국가대중교통DB 역좌표 + 노선별 역순서).

```
그래프:
  · ride edge    : 같은 노선 인접역 (≈2분/구간 + 정차)
  · transfer edge: 같은 역사 다른 노선 (환승 패널티 3~5분 + 배차/2 대기)
출발: 집 centroid → 최근접 역 (Haversine 도보)
도착: 직장 → 최근접 역
→ Dijkstra/A* → (소요분, 환승횟수). 외부 호출 0.
```

이게 삼산동 문제를 직접 푼다 — 라우터가 "삼산동=인천1호선→부평환승, 소사본동=경인선 직통"을
*알고* 계산.

**한계 (솔직히):**
- 버스 구간 약함 — 지하철 그래프만으론 집→역/역→직장 도보만 Haversine. 순수 버스 통근지 과소평가
  → 도보 접근 거리 상한(1.5km↑ 페널티) 필요
- 환승 대기 = 배차/2 가정은 지하철 배차 데이터 있어야 정확. 없으면 노선별 평균(2~6분) 상수로 시작
- 캘리브레이션은 ODsay/실측 표본 수십 건으로

### 7.1 ③ 실측 결과 (2026-06-04) — **"거짓 음성" 가설이 데이터로 반증됨**

> 표본: 서빙 universe 923동 중 50km 내 동을 거리대별 층화추출, 강남역·부천시청 각 120동 ODsay 실측.
> 원자료: `server/doc/2026-06-04/commute-accuracy-samples.json`.

**핵심 1 — 직선추정은 과대가 아니라 *과소(낙관적)*.** 추정오차(직선추정 − 실측):

| 직장 | bias(평균) | 중앙 | MAE | \|오차\|p90 |
| --- | ---: | ---: | ---: | ---: |
| 강남역 | **−5.8분** | −8.0 | 10.1 | 20 |
| 부천시청 | **−12.7분** | −12.0 | 13.3 | 26 |

→ `km/0.42`(≈25km/h) 공식이 실제보다 **빠르게** 본다. 특히 **비강남 corridor(부천)** 가 2배 더 낙관적
— 삼산동 현상(가깝지만 환승 많아 느림)이 동네 전반의 구조적 편향임이 확인됨.

**핵심 2 — 지배적 오류는 거짓음성이 아니라 *거짓양성*.** (게이트 배율 ×1.2 기준)

| 직장 · patience | 거짓음성 FN (잘린 것 중) | 거짓양성 FP (통과 중) |
| --- | ---: | ---: |
| 강남 30분 | 1.3% (~6동 외삽) | **31.1%** |
| 강남 45분 | 1.8% (~6동) | 14.1% |
| 강남 60분 | 0.0% | 10.7% |
| 부천 30분 | 0.0% | **45.5%** |
| 부천 45분 | 0.0% | **37.3%** |
| 부천 60분 | 0.0% | 13.9% |

- **FN(영구 누락) 은 미미** — 외삽해도 직장당 ~0~6동. 추정이 낙관적이라 *빠른 동을 자르는 일 자체가 드묾*.
  단, 실재하는 FN 은 고가치: 강남 patience30 의 `분당 정자동`(직선16km 추정44분→**실측 신분당 직통 20분**).
- **FP 가 진짜 문제** — 통과시킨 동의 **최대 45%** 가 실제론 인내심 초과. 예: 부천 기준 `양천구 신월동`
  (직선6.7km 추정21분 → **실측 57분**), `강서구 방화동`(8.4km 추정25분 → 49분). 가까운데 환승·우회로 느린 곳.

**시사점 (라우터 설계 재조준):**
1. 라우터의 1차 가치는 "잘린 동 구제(FN)"가 아니라 **가깝지만 느린 동의 순위 강등(FP 교정)** + 낙관 편향 제거.
   → §3 표의 우려를 데이터로 **거짓양성 쪽으로 재가중**.
2. 따라서 §7 의 후속 "클라 top-8 ODsay 재정렬"이 *지배적 오류(FP)* 를 직접 친다 — 라우터 전에도 큰 효과.
3. 라우터/추정식 캘리브레이션은 **지역별 속도 편차**(강남 vs 비강남)를 반드시 반영해야 함. 단일 25km/h 상수는
   부천권에서 −12분 편향. (라우터는 환승·노선으로 이걸 구조적으로 해결.)
4. FN 이 적다고 게이트를 더 조이면(×1.2↓) FP 는 못 줄이고 희귀 고가치 FN(정자동류)만 잃는다 — **게이트 강화가 답이 아님**.
